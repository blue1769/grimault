# Grimault — 개발용 더미 데이터셋 기대 상태 명세

> **문서 성격:** 애플리케이션 비즈니스 요구사항이 아닌, 개발 DB의 재현 가능한 테스트 픽스처 명세.  
> **기준 DDL:** [`sql/public-schema.sql`](../../sql/public-schema.sql)  
> **DB 초기화:** [`sql/dev/initialization-dev.sql`](../../sql/dev/initialization-dev.sql)  
> **데이터 적재:** [`sql/dev/seed-dev.sql`](../../sql/dev/seed-dev.sql)  
> **정합성 검증:** [`sql/dev/verify-dev.sql`](../../sql/dev/verify-dev.sql)

## 1. 목적과 범위

- 실데이터를 복사하지 않고도 계정 생성·조회·수정·삭제 및 거래 관련 API를 수동 시험할 수 있는 **작고 회계적으로 완결된 가상 가계부**를 구성한다.
- 원본 DB `grimault_db`는 그대로 두고, 별도 DB `grimault_dev_db`에서만 초기화·적재·검증한다.
- 초기 잔액과 거래 내역은 **모두 가상 데이터**로 정의한다. 실제 개인정보, 계좌번호, 원본 지출/수입 내역은 포함하지 않는다. 카드사 enum 값(`SHINHAN`, `HANA`)은 기존 코드의 허용 값만 사용한다.
- 가계부 최초 가입 시의 초기 설정 UX나 계정 생성 API의 비즈니스 규칙을 새로 정의하지 않는다.
- 거래일은 **2026-01-01 ~ 2026-03-29**로 고정하며, 실행한 날짜에 따라 결과가 변하지 않는다.

### 데이터셋의 고정 규모

| 항목 | 수량 | ID 및 특징 |
|---|---:|---|
| 금융 계정 (`account`) | 10 | 1~10 |
| 대분류 (`category`) | 11 | 1~11 |
| 소분류 (`category_item`) | 20 | 1~20 |
| 거래 헤더 (`transaction`) | 119 | 1~119 |
| 분개 (`ledger_entry`) | 238 | 거래당 정확히 2개 |
| `is_waste = true` 거래 | 6 | 거래 31·35 및 1·4·7·10주차의 카드 커피 |

119건은 **고정 시나리오 35건 + 12주 × 주간 반복 거래 7건(84건)** 으로 구성한다. 거래 ID와 마스터 ID는 고정된다. 계정 `created_at`은 `2026-01-01 00:00:00+09`, 거래 `created_at`은 이 시각에서 각 거래 ID만큼 분을 더한 값으로 고정한다. 이번 픽스처가 거래당 분개 2개를 사용한다는 사실이 애플리케이션의 모든 거래를 2분개로 제한한다는 의미는 아니다.

## 2. 계정 명세 및 기대 잔액

`ledger_entry.amount`의 부호를 그대로 누적한 **Signed Balance**를 사용한다. 자산 잔액은 양수, 미상환 카드·대출 부채는 음수, 기초자본은 음수다. 잔액이 없는 과거 계정도 조회 검증을 위해 남겨둔다.

신용카드의 `credit_card_metadata`는 현행 Kotlin `CreditCardMetadata` 필드명과 일치한다.

- 신용카드 계정에는 카드사, 결제일, 이용기간 메타데이터를 설정한다.
- 신용카드 이외 계정의 `credit_card_metadata`는 전부 `NULL`이다.
- 기초 잔액을 전액 이체한 해지 은행 계정과 사용·상환 이력이 있으나 잔액 0원인 해지 카드를 포함한다.
- 기초자본 계정은 UI 활성 계정 목록에서 제외하기 위해 `is_active=false`로 둔다.

개별 계정의 ID, 메타데이터, 활성 상태 및 기대 잔액은 `sql/dev/seed-dev.sql`에서 관리한다.

## 3. 카테고리 명세 및 기대 합계

`category.type=INCOME`에 대응하는 분개 유형은 `entry_type=REVENUE`다. 지출 카테고리 합계는 `+`, 수입 카테고리 합계는 `-` 부호를 가진다.

카테고리는 `category`(대분류)와 `category_item`(소분류)으로 구성된 2단계 구조다. 분개는 `category_item_id`로 소분류를 참조한다.

- 대분류와 소분류는 각각 활성화 상태를 가진다.
- 대분류의 정렬 순번은 전체 범위에서, 소분류의 정렬 순번은 소속 대분류 내에서 1부터 연속된다.
- 소분류는 즐겨찾기 여부(`is_favorite`)를 가지며, 초기값은 `false`다.
- 마스터에 존재하지만 거래에서는 참조되지 않는 소분류를 포함한다.
- 비활성 소분류도 과거 거래에서 참조될 수 있다.

따라서 **마스터 존재·거래 사용 여부·활성화 상태**를 구별해 검증할 수 있다.

개별 카테고리의 구성, ID, 활성 상태 및 분개 합계는 `sql/dev/seed-dev.sql`에서 관리한다.

## 4. 고정 거래 시나리오 (ID 1~35)

고정 거래 시나리오는 기초 상태 및 주요 거래 유형을 재현한다.

- 기초 자산 및 부채 설정
- 일반 소비 및 수입
- 계정 간 이체와 신용카드 대금 상환
- 현금 인출 및 선불 자산 충전
- 대출 원금 상환 및 추가 차입
- 비활성 계정·소분류를 참조하는 과거 거래

ID 1~7은 기초 상태를 구성하는 분개다. ID 7의 대출 원금은 **수입이 아니라 부채 + 자본**에 대응한다. 계좌 이체, 신용카드 상환, 대출 원금 증감, 선불머니 충전에는 손익 카테고리를 사용하지 않는다.

개별 거래의 일자, 금액 및 분개 내역은 `sql/dev/seed-dev.sql`에서 관리한다.

## 5. 반복 거래 시나리오 (ID 36~119)

2026-01-05부터 12주 동안 주 7건씩 반복한다. `w=0..11`, `slot=0..6`으로 정의한다.

- 거래 ID: `36 + 7 × w + slot`
- 거래일: `2026-01-05 + 7 × w + slot 일`
- `tags`: `fixture,weekly`
- 적요 접미사: `(01주차)` ~ `(12주차)`

반복 시나리오는 주간 외식, 장보기, 대중교통, 카드 커피, 구독료, 부수입 및 생활비 이체로 구성한다.

슬롯 4의 1·4·7·10주차만 `is_waste=true`다. 고정 거래 31·35를 더해 전체 낭비 거래는 6건이다. 금액과 분개 방향은 12주 내내 일정하다.

개별 반복 거래의 금액과 분개 내역은 `sql/dev/seed-dev.sql`에서 관리한다.

## 6. 회계 결과 및 기대 상태

초기 데이터셋은 기초자본, 자산·부채 잔액, 수입·지출을 포함하는 복식부기 구조로 구성한다.

분개 방향의 기본 규칙은 다음과 같다.

- 은행 지출: `ASSET - / EXPENSE +`
- 카드 구매: `LIABILITY - / EXPENSE +`
- 수입 입금: `ASSET + / REVENUE -`
- 카드 대금 상환: `ASSET - / LIABILITY +`
- 계정 간 이체·충전: 출금 주체 `- /` 입금 주체 `+`
- 신용카드 기반 선불 충전: `LIABILITY - / ASSET +`
- 기초 자산: `ASSET + / EQUITY -`, 기초 부채: `LIABILITY - / EQUITY +`

각 거래의 분개 금액 합계는 0이어야 한다.

계정별 잔액과 손익 합계 등 초기 데이터셋의 구체적인 결과는 `sql/dev/seed-dev.sql`에 정의된 데이터를 기준으로 한다.

## 7. 파일별 책임 및 검증 범위

| 파일 | 목적 | 실행 시점 |
|---|---|---|
| `initialization-dev.sql` | 개발 환경별 최초 1회, 테스트용 DB·접속 역할을 수동 구성하는 가이드 및 SQL | 환경 최초 설정 |
| `seed-dev.sql` | 가상의 마스터 데이터·기초자본·거래·분개를 같은 초기 상태로 재구성 | 최초 적재 및 필요 시 재시딩 |
| `verify-dev.sql` | 현재 저장된 데이터의 **구조적·회계적 무결성** 진단 | 시딩 직후 **및** API 개발 도중 |
| `seed-data-spec.md` | 픽스처 구성과 검증 원칙을 사람이 이해할 수 있도록 명세 | 코드 리뷰 및 데이터 이해 |

### `verify-dev.sql`이 검사하는 것

- **거래별 Zero-Sum**: `transaction_id`마다 분개 금액 합계가 0인지 확인한다.
- **분개 누락**: 분개가 0건이거나 1건뿐인 거래 헤더를 찾는다. 분개가 3건 이상인 거래는 허용한다.
- **참조 칼럼 누락·중복**: 분개의 `account_id`, `category_item_id`가 모두 `NULL`이거나 동시에 지정된 레코드를 찾는다.
- **현황 조회**: 다섯 테이블의 건수와 원장 전체 합계를 표시한다. 해당 값들은 정보이며 고정값과 비교해 실패시키지 않는다.

검출된 오류는 `transaction_id`, `ledger_entry_id`, 오류 유형과 설명으로 표시한다. 검출된 위반이 없으면 `PASS` 1행을 출력한다. 파일 전체가 `SELECT` 문으로 구성되어 데이터는 변경하지 않는다.

**시딩 직후와 개발 도중의 검증 기준은 동일하다.** 초기 픽스처에서 계정·거래를 추가·수정·삭제하는 행위 자체는 오류로 판단하지 않는다.

### `verify-dev.sql`이 검사하지 않는 것

- **고정 레코드 수**, 개별 레코드 내용·ID·생성 일시, 시드 전체의 정확한 일치 여부
- 계정별 기대 잔액, 카테고리별 기대 합계, 수입·지출 금액 등 **초기 시나리오 스냅샷**
- Account Type/Subtype 조합, 카드 메타데이터, `entry_type`과 계정·카테고리 유형의 매핑 등 **API 비즈니스 규칙**
- FK·UNIQUE 등 DBMS가 이미 보장하는 무결성 제약의 반복 검사
- 개별 API 요청이 의도한 금액과 대상을 올바르게 처리했는지에 대한 기능 테스트

초기 데이터셋의 상세 레코드와 금액은 `seed-dev.sql`에서 관리하며, 반복 실행하는 무결성 진단 SQL에 중복해서 구현하지 않는다.

## 8. 실행 방법 — SQL Query Console에서 수동 구성

### 최초 환경 구성 (개발 환경별 1회)

1. 기존 PostgreSQL 인스턴스의 **관리자 연결**을 DataGrip에서 연다. `postgres` 같은 관리용 데이터베이스에 연결한다.
2. `sql/dev/initialization-dev.sql`의 `[1]`~`[3]` SQL 문을 **각각 선택하여 한 번씩 실행**하고 결과를 확인한다. `CREATE DATABASE`는 트랜잭션 블록 밖에서 실행하므로 DataGrip의 Auto-commit 설정을 사용한다.
3. 관리자의 연결 대상을 새 `grimault_dev_db`로 변경하고 `[4]`의 `GRANT`를 실행한다.
4. `grimault_dev`의 비밀번호를 DataGrip의 Role/User 편집 기능 또는 별도의 **커밋하지 않을 SQL 콘솔**에서 설정한다. 비밀번호를 저장소 SQL에 쓰지 않는다.
5. `database=grimault_dev_db`, `user=grimault_dev`로 새 데이터 소스/콘솔을 열어 연결을 확인한다.
6. 기존 **`sql/public-schema.sql`**을 열어 새 개발 DB에 적용한다. PostgreSQL 트랜잭션 안에서 DDL 전체를 실행하고, 모두 성공한 경우에만 `COMMIT`한다. 실행 중 오류가 있으면 `ROLLBACK` 후 원인을 확인한다. (DataGrip에서는 수동 트랜잭션 모드 사용.)
7. `initialization-dev.sql` 하단의 테이블 조회를 실행해 다섯 테이블이 생성되었는지 확인한다.

`initialization-dev.sql`에는 연결 전환이나 스키마 적용을 자동 수행하는 `psql` 메타 명령이 없다. **파일 전체를 일괄 실행하지 않고** 명시된 연결에서 SQL 한 문장씩 실행한다. 기존 `grimault_db`와 Docker Compose는 변경하지 않는다.

### 데이터 적재·검증 (개발 중 반복)

1. DataGrip에서 연결 대상이 **`grimault_dev_db` / `grimault_dev`**인지 직접 확인한다.
2. `sql/dev/seed-dev.sql`을 하나의 SQL 스크립트로 실행한다. `BEGIN`~`COMMIT` 안에서 다섯 테이블을 `TRUNCATE ... RESTART IDENTITY` 한 뒤 픽스처를 다시 적재한다. 기존 API 테스트로 변경된 데이터는 사라진다.
3. `sql/dev/verify-dev.sql`을 실행한다. 첫 번째 결과 집합은 현재 건수·원장 합계, 두 번째 결과 집합은 `PASS` 또는 문제 레코드별 `FAIL` 목록이다.
4. API 개발 중에 데이터가 바뀌었을 때에도 **같은 `verify-dev.sql`**로 무결성을 확인한다. 초기 상태로 되돌리고 싶을 때만 `seed-dev.sql`을 재실행한다.

시드 자체의 예상 수량은 1절의 계정 10개, 대분류 11개, 소분류 20개, 거래 119건, 분개 238건을 참고한다. 이는 최초 시드의 **사람이 확인할 수 있는 안내값**이며 검증 스크립트의 실패 조건은 아니다.

### 애플리케이션 연결

Spring Boot JDBC URL의 DB 명칭은 **기본값 없는** `${DB_NAME}` 환경변수로 지정한다. 개발 시 `DB_NAME=grimault_dev_db`, `DB_USERNAME=grimault_dev` 및 개발 계정 비밀번호를 사용한다. 이번 산출물에는 `application.yml` 변경을 포함하지 않는다.

## 9. 비포함 범위

이 픽스처는 신규 사용자 온보딩, 실데이터 복제, 마이그레이션 로직 수정, API Validation 구현, Docker Compose 수정, Testcontainers 도입, `public-schema.sql` 변경, DB 프로비저닝 자동화 또는 복구 자동화를 포함하지 않는다. `raw` / `stage` 데이터를 만들지 않고 애플리케이션 원장인 `public` 영역만 구성한다.
