# 데이터 클렌징 및 마이그레이션 실행 전략

## 마이그레이션 파이프라인 아키텍처 (Medallion Pattern)
### 3단계 파이프라인 구조

> [!IMPORTANT]
> Raw 🥉`Bronze` ➔ Stage 🥈`Silver` ➔ Public 🥇`Gold`

### 계층별 역할 및 책임 (Separation of Concerns)
- `raw` 🥉 (Bronze, 원천 데이터 보존)
  - 네이버 가계부 원본 덤프 보존 (Text-only)
  - 제약조건 없이 원본 형태를 100% 보존하여 데이터 유실 없는 감사 로그(Audit Trail) 역할 수행
- `stage` 🥈 (Silver, 기술적 구문 정제 및 노이즈 원천 차단)
  - 타입 캐스팅: 한글 포함한 날짜, 문자열 콤마 금액, 빈 문자열 등 선처리
  - 노이즈 1차 필터링: 기확정된 정책 선반영 (하기 0원 거래 35건, 출금 수단 결측 오기입 1건 등)
  - 조기 실패 (Fail-Fast): 타입 변환 에러 및 포맷 이상치를 색출하여 사전 차단
- `public` 🥇 (Gold, 코어 복식부기 원장)
  - 선정제 절차를 거친 `stage` 데이터를 기반으로 순수 회계 도메인 로직만 수행
  - 계정 매핑, 카테고리 조인, 1:1 트랜잭션 헤더 및 Zero-Sum 복식부기 분개 적재

### 아키텍처 도입 이점
- 괴물 쿼리 방지: 작업 간 복잡도 상쇄, 변환 쿼리를 **기술 정제**와 **도메인 매핑**의 2단계로 분리하여 가독성 및 유지보수성 확보
- 재현성 및 멱등성 보장: 마이그레이션 검증 실패 시 `public` 원장 오염을 사전에 방어, `stage` 단위 내 안전한 디버깅 환경 확보
- 최종 릴리즈(Cut-off) 파이프라인 표준화: 릴리즈 후 증분 반영 시 일관된 파이프라인 유지 가용성 확보

## 1단계: 마스터 데이터 시드 적재
### 1. 금융 계정 `public.account` 등록
- 전체 지출/수입 이력에서 등장한 고유 계정 31개를 추출 및 적재 (`raw.outgo`, `raw.income`)
- 현재 실사용 중인 계정에 `is_active = true`, 나머지는 `is_active = false`
- 각 계정별 자산 유형 (`type`, `sub_type`) 및 (신용카드) 결제일 (`settlement_day`) 매핑

### 2. 분류 카테고리 `public.category` 등록
- 원본 데이터 상 2단계 분류 전체를 고유 값으로 추출 및 적재 (`parent_name`, `sub_name`)
- 단, 네이버 가계부에서 분류로 다루는 '이체/대체', '카드대금'의 경우 복식부기 분개 대상이므로 제외
- 원본 내 일회성으로 등장한 일부 카테고리는 대표 카테고리로 통합 (데이터 점검 간 3건 발견)
- 각 대분류의 '기타' 항목 매핑 항목 752건은 기록 보존을 위해 그대로 유지

## 2단계: 거래 헤더 `public.transaction` 및 분개 원장 `public.ledger_entry` 마이그레이션
### 3. 일반 소비 지출 및 단순 수입 (전체 데이터의 약 90%)
- 원본 내 현금/카드 동시 결제 건 0건이므로 일반 지출 및 수입은 1:1 분개로 대응 가능
- 지출: 자산/부채 계정 감소(-) 1건 + 비용 `EXPENSE` 카테고리 인식(+) 1건
- 수입: 자산 계정 증가(+) 1건 + 수익 `REVENUE` 카테고리 인식(-) 1건

### 4. 계정 간 이체 및 대체 변환
- 원본 데이터 상 '이체/대체' 대분류에 속한 지출 데이터를 **자산 간 이동 거래**로 변환
- 출금 계정 자산 감소(-) 1건 + 대상 계정 자산 증가(+) 1건으로 분개 `category_id is null`

### 5. 신용카드 대금 상환 변환
- 원본 데이터 상 '카드대금' 대분류에 속한 지출 데이터를 **부채 청산 거래**로 변환
- 출금 통장 자산 감소(-) 1건 + 신용카드 부채 감소/청산(+) 1건으로 분개 (손익 왜곡 차단)

### 6. 선불 충전 교정 (약 150여 건)
- 현금 충전: 출금 통장 자산 감소(-) 1건 + 대상 선불 자산 증가(+) 1건으로 분개 (예: 쿠팡, 네이버 등)
- 카드 충전: 신용카드 부채 증가(-) 1건 + 선불 자산 증가(+) 1건으로 분개 (예: 스타벅스, 미용실 등)

## 3단계: 무결성 검증 및 밸런스 점검
### 7. Zero-Sum 불변식 검증
- 전체 분개 합계가 정확히 `0.00`인지 검증
  ```sql
  SELECT sum(amount) FROM public.ledger_entry;
  ```

### 8. 계정 단위 잔액 대조
- 각 계정별 최종 잔액이 원본 데이터 총 잔액과 일치하는지 대조
  ```sql
  SELECT sum(amount) FROM public.ledger_entry WHERE account_id = {id};
  ```

## 4단계: 원본 데이터 특이사항 및 예외 보정 규약
### 0원 거래 제외 및 할부/선결제 이력 수용 정책
1. 대상 데이터
- `raw.outgo` 내 현금/카드 결제액이 모두 0원인 거래 총 35건
- Condition
  ```sql
  where replace(cash_amount, ',', '')::bigint = 0
    and replace(card_amount, ',', '')::bigint = 0
  ```

2. 형태별 데이터 사유: 레거시 단식부기 방어흔
- 교통카드 0원 환승 기록: 금액 변동 없이 이동 동선 기록을 위해 남겨둔 교통비 내역
- 일시불 ➔ 할부 전환 원거래 무력화: 카드사 분할납부 신청 후 원거래 이중 지출 집계 방어를 위한 수기 수정
- 할부 중도 완납(선결제) 잔여 회차 무력화: 할부 이용 중 계좌 선결제로 전액 상환 후 잔여 회차 예정 행을 0원으로 수기 수정
- 결제 취소 및 예약금 환불: 승인 취소 또는 반환된 거래의 감사 목적 메모 보존

3. 마이그레이션 보정 규약
- 회계적 실체(자산/부채 변동)가 없으므로 `ledger_entry` 및 `transaction` 생성 대상에서 전면 배제
- 단, 기존 분할 청구 및 선결제 행은 결산 통계의 연속성을 위해 소급 병합 등을 하지 않고 일체 정상 지출 거래로 수용
- 중도 선결제 출금 건 역시 은행 계정에서 실제 금액 지출로 정합성을 맞추어온 바, 원본 그대로 이관

4. 정합성 검증 결과: 이상 없음
- 0원 더미 행 35건을 제외하더라도 실제 구매 비용 및 통장 출금액, 카드 청구액이 오차 없이 100% 일치
